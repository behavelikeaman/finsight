# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다.
단, **금액 계산의 정확성과 금융 데이터 격리는 속도와 바꾸지 않는다.** 이 둘은 제품 신뢰의 전제조건이므로 MVP에서도 타협하지 않는다.

---

### ADR-001: Next.js 16 App Router + TypeScript strict + Tailwind v4
**결정**: 풀스택을 Next.js 하나로. 별도 백엔드 없이 라우트 핸들러가 API 레이어다. 최신 메이저(16)를 쓴다.
**이유**: 배포 단위가 하나라 인프라 작업이 사실상 0. 새 프로젝트라 레거시 부담이 없고, 15로 고정하면 오히려 세션이 최신 관례를 쓰려다 충돌한다.
**트레이드오프**: Next 16·Tailwind v4는 축적된 자료가 적다. `next lint`가 없어 ESLint flat config를 직접 구성해야 하고, Tailwind v4는 CSS-first `@theme`이라 config 파일 기반 관례가 통하지 않는다.

### ADR-002: Supabase (Auth + Postgres + RLS)
**결정**: 인증·DB·행 수준 보안을 Supabase 하나로.
**이유**: MVP에서 붙일 것이 가장 적다. 특히 RLS로 금융 데이터 격리를 DB 레이어에서 강제할 수 있어, 애플리케이션 코드의 실수가 데이터 유출로 이어지지 않는다.
**트레이드오프**: 벤더 종속. Auth 교체 시 세션 처리 전반을 재작성해야 한다. RLS 정책 디버깅이 ORM 쿼리보다 낯설다.

### ADR-003: Polar를 결제 게이트웨이로
**결정**: Stripe/토스페이먼츠 대신 Polar.
**이유**: Merchant of Record라 부가세·인보이스를 Polar가 처리한다. 한국 사업자가 글로벌 구독을 받을 때 정산 구조가 단순하고, 개발자향 SaaS 구독에 특화돼 웹훅·체크아웃 구현량이 적다.
**트레이드오프**: 국내 카드 커버리지와 원화 결제 UX는 토스페이먼츠보다 약하다. 수수료율이 순수 PG보다 높다. 국내 전용 피벗 시 교체가 필요하다.

### ADR-004: 집계 후 요약본만 LLM에 전달
**결정**: 거래 원문을 LLM에 넣지 않는다. 코드가 분류·집계한 결과만 Claude에 전달하고 해석·제안만 받는다.
**이유**: (1) 금액 합계를 LLM이 계산하면 틀릴 수 있고, 가계부 제품에서 이건 치명적이다. (2) 토큰 비용이 거래 건수와 무관해져 원가 예측이 가능하다. (3) 개인 금융 원문의 외부 전송량이 최소화된다.
**트레이드오프**: 규칙 기반 분류 정확도가 LLM 분류보다 낮아 미분류 가맹점이 "기타"로 쌓인다. 개선은 미분류 건만 LLM 배치 분류하는 단계를 나중에 덧붙인다.

### ADR-005: Claude 단일 제공자, 추상화 없음
**결정**: `services/claude.ts` 하나만 만든다. `AnalysisProvider` 같은 인터페이스를 두지 않는다.
**이유**: 구현체가 하나뿐인 추상화는 비용만 있고 이득이 없다.
**트레이드오프**: 제공자 교체 시 호출부를 손봐야 한다. 단 호출이 `services/` 안에 갇혀 있어 변경 범위는 파일 하나 수준.

### ADR-006: 비로그인 업로드 허용 + 결과 직전 계정 연결
**결정**: 로그인 없이 업로드·집계까지 진행하고, 결과를 저장하는 시점에 Google 계정 연결을 요구한다.
**이유**: 사용자가 자기 파일을 이미 투자한 뒤라 가입 저항이 가장 낮은 지점이다.
**트레이드오프**: 익명 세션 관리가 추가된다. 다만 ADR-012로 그 비용을 크게 줄였다.

### ADR-007: 라이트모드 고정
**결정**: 다크모드를 지원하지 않는다.
**이유**: 테마 분기가 없으면 컴포넌트·차트 색 검증 비용이 절반. 금융 SaaS의 신뢰감 문법은 밝은 배경 쪽에 축적돼 있고, 인쇄(PDF 대체)와도 자연스럽게 이어진다.
**트레이드오프**: 다크모드 선호 사용자의 불만. 나중에 추가하려면 색상 토큰 재정의가 필요하므로, 색은 Tailwind 테마 토큰으로만 쓰고 하드코딩하지 않는다.

### ADR-008: 플랜 게이팅은 서버에서만 판정
**결정**: Pro 전용 기능의 접근 판정은 전부 라우트 핸들러/Server Component에서 한다. 잠긴 데이터는 **서버가 값을 보내지 않는다.**
**이유**: 클라이언트 판정은 우회 가능하고, CSS 블러는 개발자도구로 걷힌다. 우회 시 LLM 비용이 직접 발생한다.
**트레이드오프**: 프론트에서 즉시 분기할 수 없어 일부 UI가 서버 왕복을 기다린다.

### ADR-009: 브라우저 전처리 + 정규화 배열 전송
**결정**: 파싱·헤더 매핑을 브라우저에서 수행하고, 서버에는 **원본 파일이 아니라 정규화된 거래 배열**을 JSON으로 보낸다. 서버는 배열을 검증한 뒤 직접 재집계한다.
**이유**: (1) 매핑 드롭다운마다 서버 왕복이 있으면 UX가 죽는다. (2) 요청 본문 크기 제한을 건드리지 않는다. (3) 카드번호와 원본 파일이 서버에 아예 도달하지 않는다. (4) `lib/`을 순수 함수로 둔 덕에 같은 코드가 양쪽에서 돈다.
**트레이드오프**: 클라이언트가 보낸 행을 신뢰하게 된다. 다만 조작해도 **자기 데이터만** 손상되고, 비용 남용은 10,000행 상한과 본문 크기 상한으로 방어한다.

### ADR-010: 익명 단계에서 LLM을 호출하지 않는다
**결정**: 분석을 2단계로 나눈다. `/api/analyze`는 집계만(익명 가능, LLM 0원), 인사이트는 계정 연결 후 `/api/analyses/:id/insight`에서 생성한다.
**이유**: 프리뷰는 어차피 인사이트 본문을 보내지 않는다. 그렇다면 익명 단계에서 LLM을 부를 이유가 없다. 이 분리로 비용 남용 표면이 사라지고, 집계를 먼저 렌더할 수 있으며, LLM이 실패해도 집계는 살아남는다.
**트레이드오프**: 계정 연결 직후 인사이트 생성 대기가 생긴다. 프리뷰 문구는 "로그인하면 AI 분석을 생성합니다"로 정직하게 표기한다 — 없는 결과를 블러로 위장하지 않는다.

### ADR-011: 엑셀 파싱은 ExcelJS
**결정**: SheetJS(`xlsx`) 대신 ExcelJS.
**이유**: npm 레지스트리의 `xlsx`는 0.18.5에서 멈췄고 이후 보안 수정본이 올라오지 않는다. **외부 사용자 파일을 파싱하는 금융 앱**에서 패치 경로가 없는 파서는 받아들일 수 없다.
**트레이드오프**: 기능·포맷 호환성은 SheetJS가 더 넓다. 읽기 전용 용도라 실질적 제약은 작다고 판단.

### ADR-012: Supabase 익명 로그인 + manual identity linking
**결정**: 자체 `claim_token` 메커니즘 대신 Supabase 익명 로그인을 쓴다. 파일 드롭 시점에 `signInAnonymously()`로 진짜 `auth.uid()`를 받고, 계정 연결 시 `linkIdentity('google')`로 uid를 유지한다.
**이유**: 토큰 발급·해시 저장·대조·claim 트랜잭션·24시간 정리·RLS 우회 경로가 전부 사라진다. 익명 사용자도 진짜 uid를 가지므로 **RLS가 처음부터 예외 없이 동작한다.**
**트레이드오프**:
- Supabase 대시보드에서 Anonymous Sign-In과 Manual Linking을 켜야 한다. 안 켜면 전체 플로우가 죽는다
- 익명 세션에 결과가 있을 때 `signInWithOAuth()`를 부르면 새 계정이 생겨 결과를 잃는다. 두 진입 경로의 분기를 한 곳에서만 판정해야 한다
- 기존 Google 계정과의 병합은 지원하지 않는다
- 버려진 익명 계정이 `auth.users`에 쌓인다. 드롭 시점 생성으로 크게 줄였고, 잔여분 정리는 다음 phase

### ADR-013: 계정 삭제 대신 데이터 삭제
**결정**: `DELETE /api/account`는 앱 데이터 삭제 + 로그아웃만 한다. `auth.users` 행은 남긴다.
**이유**: `auth.users` 삭제는 admin API가 필요한데, service role 사용을 웹훅 한 곳으로 제한한 원칙(ADR-008 계열)과 충돌한다. 금융 데이터 삭제 요구는 앱 데이터 삭제로 충족된다.
**트레이드오프**: 계정 껍데기가 남는다. 따라서 **UI에 "계정 삭제"라고 표기하지 않는다** — 사용자가 계정이 사라졌다고 믿는데 남아 있으면 그 자체가 신뢰 문제다. "내 데이터 전체 삭제"로 쓰고, 계정 삭제는 다음 phase.
