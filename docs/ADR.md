# Architecture Decision Records

## 철학
MVP 속도 최우선. 외부 의존성 최소화. 작동하는 최소 구현을 선택한다.
단, 세 가지는 속도와 바꾸지 않는다 — **사용자 금융정보의 취급, 금액 계산의 정확성, AI 호출 원가.** 앞의 둘은 되돌릴 수 없는 사고를 내고, 마지막은 성장할수록 손해가 커지는 구조를 만든다.

> **번호 주의**: 이 문서의 ADR 번호는 두 계열의 초안을 통합하며 1~20으로 새로 부여했다. 이전 초안의 번호와 대응하지 않는다.

---

### ADR-001: 타겟을 프리랜서·1인 사업자로 한정
**결정**: 일반 개인 소비자 가계부가 아닌, 사업/개인 경비 분리가 필요한 프리랜서를 정면으로 겨냥한다.
**이유**: 개인 소비자 소비분석은 뱅크샐러드·토스가 마이데이터 자동 연동으로 무료 제공 중이다. 수동 업로드를 요구하는 우리 제품이 이길 수 없다. 반면 "이 결제가 미팅인가 개인 커피인가"는 자동 분류가 안 되고, 절세라는 금액 환산 가능한 가치가 있어 구독 저항이 낮다.
**트레이드오프**: TAM이 작아진다. 개인 소비자 시장을 포기한다. 수요가 신고철에 몰려 월 구독 정당화가 약하므로, 규칙 학습과 히스토리로 상시 가치를 만들어야 한다.

### ADR-002: 파일 업로드 (마이데이터 연동 아님)
**결정**: 사용자가 카드사에서 직접 내려받은 CSV/엑셀을 업로드한다.
**이유**: 마이데이터 사업자는 금융위 허가 사항으로 자본금·보안 요건이 초기 단계에서 충족 불가능하다.
**트레이드오프**: 수동 업로드라는 큰 마찰을 감수한다. 이는 선택한 전략이 아니라 제약이며, 규모가 되면 마이데이터 연동이 이 제품의 해자가 된다.

### ADR-003: Next.js 16 단일 저장소 + TypeScript strict + Tailwind v4
**결정**: 풀스택을 Next.js 하나로. 별도 백엔드 없이 라우트 핸들러가 API 레이어다. 최신 메이저(16)를 쓴다.
**이유**: 1인 개발에서 백엔드 분리는 배포·인증 전달·타입 공유 비용이 이득보다 크다. 무거운 통계는 코드가 하므로 pandas가 필요 없다. 새 프로젝트라 레거시 부담이 없고, 15로 고정하면 오히려 세션이 최신 관례를 쓰려다 충돌한다.
**트레이드오프**: Next 16·Tailwind v4는 축적된 자료가 적다. `next lint`가 없어 ESLint flat config를 직접 구성해야 하고, Tailwind v4는 CSS-first `@theme`이라 config 파일 기반 관례가 통하지 않는다. 향후 배치 처리나 ML 파이프라인이 필요해지면 별도 서비스를 붙여야 한다.

### ADR-004: Supabase (Auth + Postgres + RLS)
**결정**: 인증·DB·행 수준 보안을 Supabase 하나로.
**이유**: MVP에서 붙일 것이 가장 적다. 특히 RLS로 금융 데이터 격리를 DB 레이어에서 강제할 수 있어, 애플리케이션 코드의 실수가 데이터 유출로 이어지지 않는다.
**트레이드오프**: 벤더 종속. Auth 교체 시 세션 처리 전반을 재작성해야 한다. RLS 정책 디버깅이 ORM 쿼리보다 낯설다.

### ADR-005: Polar를 결제 프로바이더로 사용
**결정**: 토스페이먼츠·포트원 대신 Polar(Merchant of Record)를 쓴다.
**이유**: PG 심사 리드타임 없이 즉시 붙일 수 있고, 부가세·인보이스 처리를 대행한다. 구독 관리가 내장되어 있다.
**트레이드오프**: Stripe 기반이라 국내 전용 카드 결제가 실패할 수 있고, 한국 정산 지원 여부도 확인이 필요하다. 수수료율이 순수 PG보다 높다. **결제 구현 step에서 Polar 문서로 두 항목을 검증한 뒤 진행할 것.** 문제가 있으면 이 ADR을 뒤집고 토스페이먼츠로 간다.

### ADR-006: 브라우저 전처리 + 정규화 배열 전송
**결정**: 파싱·헤더 매핑을 브라우저에서 수행하고, 서버에는 **원본 파일이 아니라 정규화된 거래 배열**을 JSON으로 보낸다. 서버는 배열을 검증한 뒤 직접 재집계한다.
**이유**: (1) 매핑 드롭다운마다 서버 왕복이 있으면 UX가 죽는다. (2) 요청 본문 크기 제한을 건드리지 않는다. (3) 카드번호와 원본 파일이 서버에 아예 도달하지 않아, **원본 보관·삭제 정책 자체가 필요 없어진다.** (4) `lib/`을 순수 함수로 둔 덕에 같은 코드가 양쪽에서 돈다.
**트레이드오프**: 클라이언트가 보낸 행을 신뢰하게 된다. 다만 조작해도 **자기 데이터만** 손상되고, 비용 남용은 10,000행 상한과 본문 크기 상한, 쿼터로 방어한다.

### ADR-007: 컬럼 매핑은 휴리스틱 + 사용자 교정 (AI 추론 아님)
**결정**: 헤더를 AI로 추론하지 않는다. 문자열 휴리스틱으로 날짜/가맹점/금액 컬럼을 추측하고, 사용자가 드롭다운으로 교정한다.
**이유**: AI 추론은 첫 사용자에게 지연과 실패 가능성을 지우고, 카드사 지문 캐싱을 붙여도 캐시 미스 시 여전히 실패한다. 휴리스틱은 AI 호출 0·지연 0이며, 틀려도 사용자가 즉시 고친다. 매핑은 3개 컬럼을 고르는 문제라 사람이 1초에 확인한다.
**트레이드오프**: 휴리스틱이 자주 틀리면 사용자가 매번 교정해야 한다. 교정 비율을 H2 지표로 관측하고, 임계치를 넘으면 그때 AI 추론을 덧붙인다.
**주의**: 인코딩은 휴리스틱이 해결하지 않는다. UTF-8 실패 시 CP949 폴백을 직접 구현해야 하며, 빠뜨리면 가맹점명이 전부 깨져 분류가 통째로 망가진다.

### ADR-008: 엑셀 파싱은 ExcelJS
**결정**: SheetJS(`xlsx`) 대신 ExcelJS.
**이유**: npm 레지스트리의 `xlsx`는 0.18.5에서 멈췄고 이후 보안 수정본이 올라오지 않는다. **외부 사용자 파일을 파싱하는 금융 앱**에서 패치 경로가 없는 파서는 받아들일 수 없다.
**트레이드오프**: 기능·포맷 호환성은 SheetJS가 더 넓다. 읽기 전용 용도라 실질적 제약은 작다고 판단.

### ADR-009: 민감정보 제거 후 국외 전송
**결정**: 카드번호·계좌번호·성명은 전송 전 제거하고, 거래내역(가맹점·금액·일시)은 그대로 Anthropic API로 보낸다. 개인정보 처리방침에 국외 이전을 명시하고 별도 동의를 받는다.
**이유**: 가맹점명을 익명화하면 분류 품질이 붕괴해 제품이 사라진다. 반면 카드번호는 분류에 무용하므로 보낼 이유가 없다.
**트레이드오프**: 거래내역 자체는 여전히 국외로 나간다. 이를 숨기지 않고 업로드 화면에서 명시하는 방식으로 다룬다.
**주의**: ADR-006 덕에 카드번호는 매핑 단계에서 이미 버려지지만, `lib/redact.ts`는 **2차 방어선으로 유지한다.** 가맹점명 필드에 이름이 섞여 들어오는 경우가 있다.

### ADR-010: 세무 조언을 하지 않는다
**결정**: 거래 분류와 계정과목 매핑까지만 한다. "경비 처리 가능/불가", "한도 초과" 같은 판단은 생성하지 않는다.
**이유**: 세법 판단이 틀리면 사용자가 가산세라는 실금전 손해를 본다. 세무사가 아닌 서비스의 세무 조언은 법적 회색지대이기도 하다.
**트레이드오프**: 가장 매력적으로 보이는 기능을 포기한다. 대신 분류 화면에 "최종 판단은 세무 대리인과 상의" 고지를 상시 노출한다.

### ADR-011: 확신도 기반 검토 유도
**결정**: 분류 결과에 확신도를 함께 산출하고, 낮은 건만 "확인 필요"로 상단에 모은다. 전건 확인을 강제하지 않는다.
**이유**: 결과만 보여주면 사용자가 틀린 분류를 그대로 신고에 쓰고, 전건 확인을 요구하면 자동화의 의미가 없다.
**트레이드오프**: 확신도가 높은데 틀린 건은 그대로 통과한다.

### ADR-012: 사용자 수정을 규칙으로 학습
**결정**: 사용자가 고친 분류를 `user_rules`에 저장하고, 다음 분석 때 AI 호출 전에 선적용한다. 모델 파인튜닝은 하지 않는다.
**이유**: 같은 걸 매번 고치게 하면 두 번째에 이탈한다. 규칙으로 미리 처리한 거래는 AI에 보내지 않으므로 원가도 내려간다 — 재방문 사용자일수록 마진이 좋아진다.
**트레이드오프**: 단순 매칭 규칙이라 맥락 의존적 예외(같은 가맹점의 미팅 vs 개인 방문)는 여전히 매번 판단이 필요하다.

### ADR-013: 티어별 횟수 제한 + 프롬프트 캐싱
**결정**: 무료 월 1회 분류 / 유료 월 10회 분류 + Q&A 100건. 무제한 요금제를 만들지 않는다. 거래내역은 프롬프트 캐시 프리픽스에 배치하고, 분류와 Q&A가 같은 프리픽스를 공유한다.
**이유**: 300건 분류 1회 원가가 약 440원이고, Q&A는 매 질문마다 전체 내역이 컨텍스트에 들어간다. 무제한을 걸면 헤비유저 한 명이 마진을 다 먹는다. 캐싱하면 후속 질의 입력비가 약 1/10로 떨어진다.
**트레이드오프**: 쿼터 안내가 UX를 복잡하게 만든다. 종량제보다 예측 가능성을 택했다.

### ADR-014: 파이프라인 3단계 분리 — 집계 / 분류 / Q&A
**결정**: `POST /api/analyze`는 집계만 하고 LLM을 호출하지 않는다. 분류는 `POST /api/analyses/:id/classify`, Q&A는 `POST /api/analyses/:id/chat`에서 한다.
**이유**: (1) 익명 사용자도 집계까지는 오므로, 집계에 LLM이 있으면 비용 남용 표면이 열린다. (2) 집계를 먼저 렌더하면 LLM 지연이 첫 화면을 막지 않는다. (3) LLM이 실패해도 집계 결과는 살아남는다. (4) 쿼터 차감 지점이 하나로 명확해진다.
**트레이드오프**: 라운드트립이 늘고 상태(분류 전/분류 중/분류 완료)를 UI가 관리해야 한다.

### ADR-015: 익명 프리뷰는 표본 20건만 분류
**결정**: 로그인 없이 업로드·집계·**상위 20건 분류**까지 허용한다. 전건 분류는 계정 연결 후. 표본은 uid당 1회(`profiles.sample_used`).
**이유**: "AI가 내 경비를 제대로 가르는가"는 직접 봐야 전달되는 가치라, 프리뷰에 실제 분류 결과가 없으면 계정 연결 동기가 생기지 않는다. 반면 전건(회당 440원)을 익명에 열면 남용 표면이 생긴다. 20건이면 세션당 약 30원이다.
**트레이드오프**: 20건으로 판단이 안 되는 사용자가 있다. 표본 대상은 금액 상위순으로 골라 판단 가치가 높은 건을 우선 보여준다. 없는 결과를 블러로 위장하지 않고 "계정을 연결하면 전체를 분류합니다"로 정직하게 표기한다.

### ADR-016: Supabase 익명 로그인 + manual identity linking
**결정**: 자체 `claim_token` 메커니즘이나 IP·브라우저 지문 제한 대신 Supabase 익명 로그인을 쓴다. 파일 드롭 시점에 `signInAnonymously()`로 진짜 `auth.uid()`를 받고, 계정 연결 시 `linkIdentity('google')`로 uid를 유지한다.
**이유**: 토큰 발급·해시 저장·대조·claim 트랜잭션·정리 작업이 전부 사라진다. 익명 사용자도 진짜 uid를 가지므로 **RLS가 처음부터 예외 없이 동작하고**, 표본 1회 제한도 지문이 아니라 uid 기준으로 걸 수 있다.
**트레이드오프**:
- Supabase 대시보드에서 Anonymous Sign-In과 Manual Linking을 켜야 한다. 안 켜면 전체 플로우가 죽는다
- 익명 세션에 결과가 있을 때 `signInWithOAuth()`를 부르면 새 계정이 생겨 결과를 잃는다. 두 진입 경로의 분기를 한 곳에서만 판정해야 한다
- 기존 Google 계정과의 병합은 지원하지 않는다
- 버려진 익명 계정이 `auth.users`에 쌓인다. 드롭 시점 생성으로 크게 줄였고, 잔여분 정리는 다음 phase

### ADR-017: 게이팅과 쿼터는 서버에서만 판정
**결정**: 유료 기능 접근과 쿼터 판정은 전부 라우트 핸들러/Server Component에서 한다. 막힌 결과는 **서버가 값을 보내지 않는다.**
**이유**: 클라이언트 판정은 우회 가능하고, CSS 블러는 개발자도구로 걷힌다. 우회 시 LLM 비용이 직접 발생한다. 클라이언트가 보낸 `mode:'full'`도 서버가 세션의 익명 여부로 재판정한다.
**트레이드오프**: 프론트에서 즉시 분기할 수 없어 일부 UI가 서버 왕복을 기다린다.

### ADR-018: 계정 삭제 대신 데이터 삭제
**결정**: `DELETE /api/account`는 앱 데이터 삭제 + 로그아웃만 한다. `auth.users` 행은 남긴다.
**이유**: `auth.users` 삭제는 admin API가 필요한데, service role 사용을 웹훅 한 곳으로 제한한 원칙(ADR-017 계열)과 충돌한다. 금융 데이터 삭제 요구는 앱 데이터 삭제로 충족된다.
**트레이드오프**: 계정 껍데기가 남는다. 따라서 **UI에 "계정 삭제"라고 표기하지 않는다** — 사용자가 계정이 사라졌다고 믿는데 남아 있으면 그 자체가 신뢰 문제다. "내 데이터 전체 삭제"로 쓰고, 계정 삭제는 다음 phase.

### ADR-019: 라이트모드 고정
**결정**: 다크모드를 지원하지 않는다.
**이유**: 테마 분기가 없으면 컴포넌트 색 검증 비용이 절반. 금융 SaaS의 신뢰감 문법은 밝은 배경 쪽에 축적돼 있고, 인쇄(PDF 대체)와도 자연스럽게 이어진다. 색을 분류 상태(사업/개인/확인필요)에만 쓰는 규칙도 단일 테마에서만 지켜진다.
**트레이드오프**: 다크모드 선호 사용자의 불만. 나중에 추가하려면 색상 토큰 재정의가 필요하므로, 색은 Tailwind 테마 토큰으로만 쓰고 하드코딩하지 않는다.

### ADR-020: Claude 단일 제공자, 추상화 없음
**결정**: `services/anthropic/` 하나만 만든다. `ClassificationProvider` 같은 인터페이스를 두지 않는다.
**이유**: 구현체가 하나뿐인 추상화는 비용만 있고 이득이 없다.
**트레이드오프**: 제공자 교체 시 호출부를 손봐야 한다. 단 호출이 `services/` 안에 갇혀 있어 변경 범위는 파일 몇 개 수준.
