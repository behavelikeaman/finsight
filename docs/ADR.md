# Architecture Decision Records

## 철학
MVP 속도 최우선. 단, 두 가지는 타협하지 않는다 — 사용자 금융정보의 취급, 그리고 AI 호출 원가. 전자는 되돌릴 수 없는 사고를 내고, 후자는 성장할수록 손해가 커지는 구조를 만든다.

---

### ADR-001: 타겟을 프리랜서·1인 사업자로 한정
**결정**: 일반 개인 소비자 가계부가 아닌, 사업/개인 경비 분리가 필요한 프리랜서를 정면으로 겨냥한다.
**이유**: 개인 소비자 소비분석은 뱅크샐러드·토스가 마이데이터 자동 연동으로 무료 제공 중이다. 수동 CSV 업로드를 요구하는 우리 제품이 이길 수 없다. 반면 "이 결제가 미팅인가 개인 커피인가"는 자동 분류가 안 되고, 절세라는 금액 환산 가능한 가치가 있어 구독 저항이 낮다.
**트레이드오프**: TAM이 작아진다. 개인 소비자 시장을 포기한다.

### ADR-002: CSV 업로드 (마이데이터 연동 아님)
**결정**: 사용자가 카드사에서 직접 내려받은 CSV를 업로드한다.
**이유**: 마이데이터 사업자는 금융위 허가 사항으로 자본금·보안 요건이 초기 단계에서 충족 불가능하다.
**트레이드오프**: 매달 수동 업로드라는 큰 마찰을 감수한다. 이는 선택한 전략이 아니라 제약이며, 규모가 되면 마이데이터 연동이 이 제품의 해자가 된다.

### ADR-003: 컬럼 매핑을 AI로 1회 추론 후 캐싱
**결정**: 카드사별 전용 파서를 작성하지 않는다. 첫 파일만 Claude가 상위 20행을 보고 컬럼 매핑을 추론하고, 카드사 지문별로 저장해 이후 결정론적으로 파싱한다.
**이유**: 국내 카드사 CSV에 표준이 없어 전용 파서는 유지보수 지옥이며, 신규 카드사마다 배포가 필요하다. 캐싱하면 첫 사용자만 비용을 내고 이후는 API 호출 0원·지연 0초·결과 일관성 100%.
**트레이드오프**: 첫 사용자는 지연과 추론 실패 가능성을 감수한다. 카드사가 포맷을 바꾸면 지문 불일치로 재추론된다.
**주의**: 인코딩은 AI가 해결하지 않는다. UTF-8 실패 시 CP949 폴백을 직접 구현해야 하며, 빠뜨리면 가맹점명이 전부 깨져 분류가 통째로 망가진다.

### ADR-004: 민감정보 제거 후 국외 전송
**결정**: 카드번호·계좌번호·성명은 전송 전 제거하고, 거래내역(가맹점·금액·일시)은 그대로 Anthropic API로 보낸다. 개인정보 처리방침에 국외 이전을 명시하고 별도 동의를 받는다.
**이유**: 가맹점명을 익명화하면 분류 품질이 붕괴해 제품이 사라진다. 반면 카드번호는 분류에 무용하므로 보낼 이유가 없다.
**트레이드오프**: 거래내역 자체는 여전히 국외로 나간다. 이를 숨기지 않고 업로드 화면에서 명시하는 방식으로 다룬다.

### ADR-005: 원본 30일 보관, 정규화 데이터 장기 보존
**결정**: 업로드 원본 CSV는 30일 후 자동 삭제. 정규화된 거래 데이터는 암호화 저장하고 구독 해지 +30일까지 유지한다.
**이유**: "지난달 대비" 같은 시계열 인사이트에는 거래 데이터 보존이 필요하다. 반면 원본에는 카드번호 전체·승인번호 등 우리가 쓰지도 않는 항목이 들어있어 유출 시 피해면이 넓다. 30일이면 파싱 오류 재처리 창구로 충분하다.
**트레이드오프**: 30일이 지난 뒤 파싱 오류가 발견되면 사용자에게 재업로드를 요청해야 한다.

### ADR-006: 세무 조언을 하지 않는다
**결정**: 거래 분류와 계정과목 매핑까지만 한다. "경비 처리 가능/불가", "한도 초과" 같은 판단은 생성하지 않는다.
**이유**: 세법 판단이 틀리면 사용자가 가산세라는 실금전 손해를 본다. 세무사가 아닌 서비스의 세무 조언은 법적 회색지대이기도 하다.
**트레이드오프**: 가장 매력적으로 보이는 기능을 포기한다. 대신 분류 화면에 "최종 판단은 세무 대리인과 상의" 고지를 상시 노출한다.

### ADR-007: 확신도 기반 검토 유도
**결정**: 분류 결과에 확신도를 함께 산출하고, 낮은 건만 "확인 필요"로 상단에 모은다. 전건 확인을 강제하지 않는다.
**이유**: 결과만 보여주면 사용자가 틀린 분류를 그대로 신고에 쓰고, 전건 확인을 요구하면 자동화의 의미가 없다.
**트레이드오프**: 확신도가 높은데 틀린 건은 그대로 통과한다.

### ADR-008: 사용자 수정을 규칙으로 학습
**결정**: 사용자가 고친 분류를 `user_rules`에 저장하고, 다음 분석 때 AI 호출 전에 선적용한다. 모델 파인튜닝은 하지 않는다.
**이유**: 같은 걸 매달 고치게 하면 두 번째 달에 이탈한다. 규칙으로 미리 처리한 거래는 AI에 보내지 않으므로 원가도 내려간다 — 재방문 사용자일수록 마진이 좋아진다.
**트레이드오프**: 단순 매칭 규칙이라 맥락 의존적 예외(같은 가맹점의 미팅 vs 개인 방문)는 여전히 매번 판단이 필요하다.

### ADR-009: 티어별 횟수 제한 + 프롬프트 캐싱
**결정**: 무료 월 1회 / 유료 월 10회 분석 + Q&A 100건. 무제한 요금제를 만들지 않는다. 거래내역은 프롬프트 캐시 프리픽스에 배치한다.
**이유**: 300건 분석 1회 원가가 약 440원이고, Q&A는 매 질문마다 전체 내역이 컨텍스트에 들어간다. 무제한을 걸면 헤비유저 한 명이 마진을 다 먹는다. 캐싱하면 후속 질의 입력비가 약 1/10로 떨어진다.
**트레이드오프**: 쿼터 안내가 UX를 복잡하게 만든다. 종량제보다 예측 가능성을 택했다.

### ADR-010: Next.js 단일 저장소 + Supabase
**결정**: Python 백엔드를 분리하지 않고 Next.js 15 App Router 하나로 간다. DB·Auth·RLS는 Supabase.
**이유**: 1인 개발에서 백엔드 분리는 배포·인증 전달·타입 공유 비용이 이득보다 크다. 무거운 통계는 Claude가 하므로 pandas가 필요 없다.
**트레이드오프**: 향후 배치 처리나 ML 파이프라인이 필요해지면 별도 서비스를 붙여야 한다.

### ADR-011: Polar를 결제 프로바이더로 사용
**결정**: 토스페이먼츠·포트원 대신 Polar(Merchant of Record)를 쓴다.
**이유**: PG 심사 리드타임 없이 즉시 붙일 수 있고, 부가세·인보이스 처리를 대행한다. 구독 관리가 내장되어 있다.
**트레이드오프**: Stripe 기반이라 국내 전용 카드 결제가 실패할 수 있고, 한국 정산 지원 여부도 확인이 필요하다. **결제 구현 단계에서 Polar 문서로 두 항목을 검증한 뒤 진행할 것.** 문제가 있으면 ADR-011을 뒤집고 토스페이먼츠로 간다.

### ADR-012: 로그인 없는 1회 체험 허용
**결정**: 랜딩에서 가입 없이 CSV를 올려 분류 결과를 볼 수 있게 한다. 저장하려면 가입.
**이유**: "AI가 내 경비를 제대로 가르는가"는 직접 봐야 전달되는 가치다. 가입 폼을 앞에 세우면 그 검증 기회를 잃는다.
**트레이드오프**: 회당 440원의 원가가 미인증 사용자에게 노출된다. IP·브라우저 지문 기준 1회 제한과 거래 100건 상한으로 방어한다.
