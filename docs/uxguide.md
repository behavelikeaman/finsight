# UI 디자인 원칙 7가지

출처: [Figma — UI 디자인 원칙](https://www.figma.com/ko-kr/resource-library/ui-design-principles/)

이 문서는 일반 원칙을 **FinSight에 어떻게 적용하는가**로 옮긴 것이다.
토큰과 컴포넌트 규격은 `DESIGN.md`가 정한다. 충돌하면 `DESIGN.md`가 이긴다.
이 문서는 "무엇을 쓰는가"가 아니라 "왜 그렇게 배치하는가"를 다룬다.

판정이 필요한 항목은 전부 **검증 가능한 형태**로 적었다. "적절히 대비를 준다"가 아니라 "4.5:1 이상"이다.

---

## 1. 계층 구조 (Hierarchy)

> 사용자가 주요 정보를 인식하고 덜 중요한 요소와 쉽게 구분하도록 돕는다.
> 크기·두께, 대비, 간격으로 만든다. 무엇을 먼저 보고 무엇을 스크롤해야 보는지를 의도적으로 정한다.

**이 제품에서**

이 브랜드는 굵기가 아니라 **크기와 간격**으로 위계를 만든다(`DESIGN.md`: display 타이포는 weight 400 고정). 제목을 굵게 만들어 위계를 세우려 하지 마라.

화면별 주인공은 하나씩이다.

| 화면 | 주인공 | 조연 |
|---|---|---|
| 랜딩 | **드롭존** | 히어로 문구, 기능 카드, 요금제 |
| 분석 상세 | **확인 필요 표** | 요약 카드, 사업경비/개인지출 표, 차트 |
| 매핑 | **컬럼 셀렉트 3개** | 미리보기 행 |

**규칙**

- 섹션 간격으로 위계를 표현한다. 모든 섹션이 같은 간격이면 위계가 없는 것이다
- 주인공 섹션은 조연보다 **간격을 1단계 크게** 준다
- "확인 필요"는 항상 최상단이다. 스크롤 아래로 밀지 마라 — 낮은 확신도가 묻히면 제품 경계(확신도 고지)가 무너진다

---

## 2. 점진적 공개 (Progressive Disclosure)

> 여러 단계로 안내하며 각 단계에서 명확한 선택을 할 만큼의 정보만 준다.
> 사용자가 현재 진행 상황과 남은 단계를 알 수 있게 한다.

**이 제품에서**

업로드는 이미 단계로 쪼개져 있다: `드롭 → 매핑 → 분석 → 표본 → 연결 → 전건`. 문제는 **사용자가 지금 어디인지 모른다**는 것이다.

**규칙**

- 다단계 흐름에는 현재 단계와 남은 단계를 보여준다
- 처리 중 상태는 텍스트 한 줄로 끝내지 않는다. 무엇을 하는 중인지 + 진행 표시
- 한 화면에서 요구하는 결정은 최소로 줄인다. 전건 분류 전에 요금제·규칙 저장·계정 연결을 동시에 묻지 마라

---

## 3. 일관성 (Consistency)

> 버튼의 모양과 작동 방식이 제품 전체에서 같으면 사용자는 인터페이스를 생각하지 않고 작업에 집중한다.
> 패턴에서 벗어날 때는 타당한 근거가 필요하다.

**이 제품에서**

`DESIGN.md`가 이미 규격을 정해 뒀다. 일관성 위반은 대부분 그 규격을 안 지킨 것이다.

**규칙**

- **버튼·탭·칩은 예외 없이 pill**(`rounded-full`). 이것이 이 브랜드의 가장 알아보기 쉬운 신호다
- 카드 반경은 라우트로 갈린다: 마케팅 `rounded-2xl`(24px), 앱 `rounded-lg`(16px)
- 폼 컨트롤(`select`·`input`)은 전부 같은 반경·높이·테두리를 쓴다
- 숫자(금액·확신도·건수)는 전부 `font-mono` + `tabular-nums`. 예외 없다
- 같은 뜻의 액션은 같은 자리에 둔다

---

## 4. 대비 (Contrast)

> 중요한 콘텐츠로 주의를 끌기 위해 전략적으로 대비를 쓴다. 보조 동작은 낮은 대비로 둔다.

**이 제품에서**

`DESIGN.md`의 색 규율이 우선한다 — **경비 분류에 빨강을 쓰지 않는다.** 개인지출은 잘못된 것이 아니다. 빨강은 파괴적 액션(데이터 전체 삭제)과 에러 전용이다.

**규칙**

- 주 액션은 `bg-primary`, 보조는 `bg-surface-strong`. 한 화면에 주 액션은 하나
- 파괴적 액션만 빨강. 그 외 어디에도 쓰지 않는다
- 대비는 색상(hue)이 아니라 명도로 만든다. 호버는 배경 한 단계만 조정하고 hue를 바꾸지 마라

---

## 5. 접근성 (Accessibility)

> 4명 중 1명 이상이 시각 장애를 겪는다. 대체 텍스트, 키보드 탐색, 보조 기술 호환, 충분한 명도 대비.

**이 제품에서**

세무 신고 시즌에 쓰는 실무 도구다. 키보드만으로 표 전체를 수정할 수 있어야 한다.

**규칙 — 전부 판정 가능한 기준이다**

- 본문·보조 텍스트는 배경 대비 **4.5:1 이상**. 비텍스트(경계선, 상태 점, 아이콘)는 **3:1 이상**
- 표 안의 모든 폼 컨트롤에 접근 이름을 준다. 시각적 라벨이 열 헤더에만 있으면 스크린리더는 그 셀렉트가 무엇인지 모른다 → `aria-label`
- 표에는 `<caption>`을, 헤더 셀에는 `scope`를 준다
- 상태 변화(저장됨, 규칙 학습됨, 실패함)는 `aria-live`로 알린다. 화면에만 뜨는 토스트는 안 읽힌다
- **정보를 색으로만 전달하지 않는다.** 분류 상태는 색 + 텍스트를 함께 쓴다
- `window.confirm`을 흐름 안에서 쓰지 마라. 스타일을 못 주고, 포커스를 빼앗고, 브라우저마다 다르게 뜬다

---

## 6. 근접성 (Proximity)

> 관련 있는 요소는 함께 배치한다. 가까이 있으면 관련 있다고 인식한다.
> 실수로 누르면 안 되는 것은 떼어 놓는다.

**이 제품에서**

**규칙**

- 파괴적 액션(데이터 전체 삭제)은 다른 액션과 **떨어뜨린다**. 구분선 아래 별도 영역에 둔다
- 한 거래를 다루는 컨트롤(분류·계정과목)은 인접시킨다
- 고지 문구는 설명하는 대상 옆에 둔다. 페이지 맨 아래로 밀면 읽히지 않는다
- 간격은 관계를 표현한다: 그룹 내부 < 그룹 사이

---

## 7. 정렬 (Alignment)

> 깔끔한 선이 디자인을 전문적으로 보이게 한다. 일관된 정렬은 가독성과 예측 가능성을 높인다.

**이 제품에서**

표가 주인공인 제품이라 정렬이 곧 가독성이다.

**규칙**

- **숫자 열은 우측 정렬, 헤더도 같이 우측 정렬한다.** 값과 헤더의 정렬이 어긋나면 열이 깨져 보인다
- 금액·확신도는 `tabular-nums`로 자릿수를 고정한다
- 모든 라우트는 같은 최대 폭(1200px)과 같은 좌우 여백을 쓴다

---

## 검증

수치 판정은 눈으로 하지 않는다.

```bash
npm run lint && npm run build && npm run test
```

대비율은 계산해서 확인한다(WCAG 2.1 상대 휘도). 토큰을 바꿀 때마다 다시 계산한다.

## 이 문서를 고칠 때

원칙 7가지는 출처가 있는 내용이므로 함부로 바꾸지 않는다.
"이 제품에서" 절과 규칙은 제품이 바뀌면 갱신한다. `DESIGN.md`와 어긋나면 `DESIGN.md`를 먼저 고치고 여기를 맞춘다.
